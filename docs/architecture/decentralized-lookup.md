# 分散ルックアップ — 中央索引なしで「X はどこか」に答える基盤

> **これは [[p-fs.md]] §6.1・[[survival-network.md]] §7・[[regions.md]] §6.2 が
> 三方向から同時にぶつかった、同じ一枚の壁である。**
> p-fs は「この hash の block はどのノードにあるか」を、
> 分散ゲーティングは「この問いに応えるべきエキスパートはどこか」を、
> world は「このオブジェクト（ノード・資源・知識）の所在は」を問う。
> 三つの問いの形は同じ：**中央の索引を一切持たずに、名前から所在を引く。**
> 本ドキュメントはその再利用可能な基盤（substrate）を設計する。
>
> [[README.md]] の唯一の不変条件をここでも繰り返す：
> **中央は、置かない。** 索引サーバも、スーパーノードも、トラッカーも。
> それを置いた瞬間、潰す価値のある一点が生まれ、映画の AI に逆戻りする。
>
> **状態 (2026-06-07)**: §6 の **L0（状態なし HRW 責任計算）と L1（解決キャッシュ＋read-k）は
> `arch/common/lookup.c` に実装済**（cross-ABI byte-stable な HRW スコアリング＋自己テスト）。
> **L2（ネット越し WANT/HAVE フォールバック＋repair-on-miss）と L3（global 昇格）は未実装＝設計のまま。**
> §1〜§5 の設計・§7 の正直な論点は引き続き有効。以下、本文の "DESIGN ONLY" は L2 以降を指す。

## 1. 問題 — 中央索引は kill switch であり、素朴な一貫性ハッシュは churn で壊れる

### 1.1 なぜ中央索引が許されないか

「どこに何があるか」を知る一点があれば、ルックアップは自明になる。DNS のルート、
BitTorrent のトラッカー、Kubernetes の etcd——どれもそうやって楽をしてきた。
だがその一点は、**ネットワーク全体の記憶への kill switch** である。索引を落とせば、
全データが物理的には無傷のまま、誰にも見つけられなくなる。体は生きているのに
名前を呼べない——失語の脳である。

[[survival-network.md]] §7 が「中央ゲートを置けば、それを潰された瞬間に全体が
止まる」と書いたのと同じ理由で、中央索引は設計から排除される。これは性能や
スケーラビリティの問題である以前に、**生存の問題**である。

### 1.2 では全員が同じ計算をすればよいか — 素朴な一貫性ハッシュの罠

中央なしの定番解はこうだ：「key（block hash / expert id / object id）をノード ID
空間へ写像し、最も近いノードを責任者とする。**全員が同じ membership から同じ
決定的計算をするので、索引は要らない**」。

この前提——*全員が同じ membership を見ている*——が、p-kernel では成り立たない。
`region.h` のコメントが正直に白状している通り：

> v1 (このファイル) は各ノードの自己中心的 (egocentric) な局所ビュー: …
> RTT の非対称性やメンバシップ差により、ノード間でビューが完全一致する
> 保証はまだ無い

SWIM は eventually consistent である。ノード C が join した直後、ノード A の
`dnode_table[]` には C が ALIVE として載っているが、ノード B にはまだ届いて
いない、という時間窓が必ず存在する。このとき：

```
  writer A の見る世界: {A, B, C}  → key k の責任者 = C と計算 → C に書く
  reader B の見る世界: {A, B}     → key k の責任者 = A と計算 → A に読みに行く
  → A は持っていない。データは C に在るのに、B には「存在しない」ように見える。
```

**書き手と読み手が異なる責任集合を計算する瞬間、書かれたものが引けなくなる。**
churn（join / leave / crash / ネットワーク分断）が起きるたびにこの窓が開く。
窓の長さは SWIM の収束時間（gossip の伝播ラウンド数 × プローブ間隔）で決まり、
ゼロにはできない。

つまり問題は二段重ねである：

1. **中央索引は置けない**（生存上の不変条件）
2. **中央なしの決定的計算は、eventually consistent な membership の上では
   「だいたい正しいが、churn の最中は外れる」**

素朴な一貫性ハッシュを「真実」として扱う設計は、2 を無視している。
p-kernel の答えは、決定的計算を**真実ではなくヒント**として扱うことだ。
これは `moe.c` が broadcast score table を「決して真実として扱わない」
（NO-CENTRAL 不変条件）と決めたのと、同じ精神の繰り返しである。

### 1.3 解くべき問いの正確な形

> **「key k を持つ者を、(a) 中央なしで、(b) membership がノード間でずれていても、
> (c) region の密/疎構造を尊重した通信量で、見つける。
> 見つからない瞬間があってもよいが、その窓は SWIM の収束時間で有界であること。」**

(a) は不変条件、(b) が本ドキュメントの主題、(c) は [[regions.md]] のスケール戦略
との合流点である。「常に見つかる」を保証しようとすると強整合（=どこかに合意点
=準・中央）が要る。それは捨てる。代わりに**「外れたら必ず別経路で見つかり、
見つけた結果が将来のルックアップを治す」**自己修復系として設計する。

## 2. アプローチ — 決定的計算（べき所）＋ gossip フォールバック（実際）＋ 解決キャッシュ（記憶）

[[p-fs.md]] §3.3 が p-fs 固有の形で先取りした三段構えを、ここで基盤として
一般化する。**①計算で当てに行き、②外れたら訊いて回り、③成功を覚える。**

### 2.1 第一段：rendezvous hashing（HRW）で「べき所」を決定的に計算する

key k の**責任集合（responsible set）** を、各ノードが自分の `dnode_table[]` から
ローカルに計算する：

```
  weight(n, k) = H(node_id_n ∥ k)          # ノードごとの擬似乱数スコア
  responsible(k, r) = ALIVE ノードを weight 降順に並べた上位 r 台
```

これは rendezvous hashing（HRW: highest random weight）である。一貫性ハッシュ
（リング）ではなく HRW を第一候補とする理由：

- **リング構築が不要**。仮想ノードのリングを維持・同期する状態が一切ない。
  「状態を持たない決定的計算」は、membership がずれている世界では美徳である
  ——ずれの源を membership 一つに限定できる。
- **ノード増減時の移動が最小**。1 台の join/leave で動く key は理論最小割合のみ。
  これは churn 窓を直接小さくする。
- **top-r が自然に出る**。weight 順位の上位 r 台がそのまま複製先になる
  （リングだと「後続 r 台」という別概念が要る）。
- 計算コストは O(N)（全 ALIVE ノードのハッシュ計算）。`DNODE_MAX` が数十〜数百の
  範囲では問い合わせ毎に都度計算してよい（`region_recompute()` が O(DNODE_MAX) を
  「安価」と割り切ったのと同じ判断）。数千ノード規模では §2.4 のとおり region で
  二段化するため、一段の N は region サイズに抑えられる。

書き込み（publish / save / expert 広告）は `responsible(k, r)` の r 台へ置く。
読み出しはまず同じ計算で当てに行く。**ノード間でビューが一致している限り、
これだけで索引なしに 1 ホップで当たる。** ずれている瞬間の救済が第二段である。

### 2.2 第二段：gossip フォールバック — region 内 WANT → global WANT

計算で当てた責任ノードが「持っていない」「応答しない」とき、**実際に持っている者を
訊いて回る**：

1. **region 内 WANT（密・第一フォールバック）**：自 region のメンバへ
   `WANT(k)` を投げる。region は RTT≤τ の密結合集合（`region.h`）なので、
   ここはブロードキャストしてよい——安い・速い・近い。持っている者が
   `HAVE(k, 所在)` を返す。
2. **global WANT（疎・第二フォールバック）**：region 内に無ければ、region の
   coordinator 経由で global スコープへ要約された `WANT(k)` を流す
   （[[regions.md]] §3.4 の K-DDS スコープ階層に乗る）。各 region で coordinator が
   region 内へ展開し、HAVE が逆経路で返る。

WANT は「フラッディング」だが、二つの構造で爆発を抑える：
**(a)** region 内はそもそも小さい（密）。**(b)** region 間は coordinator ゲートウェイ
を通る要約のみ（疎）で、TTL とレート制限を付ける。これは [[regions.md]] が
全対全 O(N²) を殺すために導入した密/疎構造を、ルックアップにそのまま再利用する形
である（詳細は §4）。

> **注意（正直に）**：coordinator は「region 内の最小 ID」という決定的に選ばれる
> 役割であって中央ではない——死ねば次の最小 IDが引き継ぐ——が、global WANT の
> 経路上では単一障害点的に振る舞う瞬間がある。coordinator 不応答時は region 内の
> 次点が代行する縮退経路を必ず併設する（§7.4 で再訪）。

### 2.3 第三段：world-table を解決キャッシュとして使う — 成功を覚える

一度解決した `k → 所在ノード` は局所に覚える。ここで新しいテーブルを発明しない。
`world.c` が既に持っている**「各ノードが自分だけの全網ビューを gossip から組み立てる」
仕組み**（world-table）が、解決キャッシュの正しい置き場所である：

- キャッシュは**各ノードのローカルな観測**であり、真実ではない（world.h の
  「古さ・不完全さの尊重」と同一の意味論）。古ければ外れ、外れれば §2.1→§2.2 が
  また走って治す。
- ホットな key は最初の 1 回以降、計算もフォールバックも踏まずに当たる。
- TTL / EWMA 的な鮮度管理は `region.c` の RTT EWMA と同じ手法を流用する。

三段をまとめると：

```
  resolve(k):
    1. world-table キャッシュに k があれば → その所在へ (外れたら 2 へ)
    2. responsible(k, r) を HRW で計算 → 上位から順に問い合わせ (read-k, §3)
    3. 外れたら region 内 WANT → さらに global WANT
    4. 解決したら world-table に記憶し、必要なら repair-on-miss (§3) を起動
```

どの段も中央を参照しない。どの段が壊れても次の段が拾う。**「決定的計算は速いが
churn に弱い／gossip は遅いが必ず実際を見つける」という相補性**が、この設計の核
である。

### 2.4 DHT か gossip フラッディングか — 規模ごとの正直な比較

| 規模 | 構造化 DHT（Kademlia 等） | HRW + gossip フォールバック（本設計） |
|---|---|---|
| 〜数十ノード | ルーティングテーブル維持が overkill。O(log N) ホップの利得なし（log 8 ≒ 3 vs 全員直接 1 ホップ） | **全 ALIVE を見て O(N) 計算・1 ホップ。最適。** |
| 〜数百ノード | 釣り合い始めるが、churn 時のテーブル修復トラフィックが重い | region 二段化（region 内 HRW + global WANT）でまだ十分回る |
| 数千ノード〜 | O(log N) ホップが効く。ただし egocentric membership 上の DHT は iterative lookup の各ホップで「相手のビュー」に依存し、ずれの伝播解析が難しくなる | global WANT の疎フラッディングがスケール限界に近づく。**region-of-regions 階層か、coordinator 層だけの DHT が必要になる（§7 未解決）** |

判断：**いま p-kernel が居る数十〜数百ノード帯では、DHT のルーティング状態は
「維持しなければならない準・索引」であり、負債のほうが大きい。** HRW は状態ゼロで
同じ「べき所」を与える。数千ノード帯で本当に必要になったとき、coordinator 層
（region の代表のみ、数は region 数）に限定した DHT を**第二階層として**載せる
余地を残す——これなら DHT のテーブルも region 局所の小さな世界に閉じる。
今それを作り込むのは、8 台上限の時代に N=10⁶ を設計する過ちの繰り返しである。

## 3. ズレ耐性 — top-k 複製・read-k・repair-on-miss、窓は SWIM 収束で有界

§1.2 のずれは消せない。消す代わりに、**ずれていても重なる確率を上げ（書きの冗長）、
重なりを探す試行を増やし（読みの冗長）、外れた事実そのものを修復の引き金にする
（repair-on-miss）**。

### 3.1 top-k responsible replication — 書きの冗長

key k を responsible(k) の**第 1 位だけでなく上位 r 台**に置く（r=複製度、
[[p-fs.md]] §2.2 の replica 数と同じパラメータ）。

なぜこれがずれに効くか：membership のずれは HRW の weight 順位を**局所的に**しか
乱さない。writer と reader のビューが ε 台ぶん違っても、両者の top-r 集合は
ほぼ重なる——1 台の join/leave が動かす順位は HRW では最小限だからだ。
**writer の top-r と reader の top-r の交わりが空でない限り、読みは成功する。**
r=1 だと一致が「完全一致」を要求するのに対し、r≥2 で要求が「集合の交差」へ緩む。
これが top-k 複製の本質的な仕事である（耐久性は副産物ですらある）。

### 3.2 read-k — 読みの冗長

読み手は自分の計算した responsible(k) の第 1 位だけを信じず、**上位から k 台
（read-k ≤ r）まで順に（または並行に）当たる**。1 台目が外れても 2 台目で当たる
確率は、ずれが独立なら指数的に改善する。レイテンシが惜しい読みは並行に投げ、
帯域が惜しい読みは逐次に倒す——この択は呼び出し側（p-fs / gating / world）が選ぶ。

### 3.3 repair-on-miss — 外れを修復の引き金にする

フォールバック（WANT）で解決に成功したとき、それは**「べき所に無かった」という
診断情報**である。解決者（または発見されたデータ保持者）は、現在の自分のビューで
計算した responsible(k, r) のうち持っていない者へデータを押し込む（push repair）。

- churn で責任集合が動いた後、アクセスされた key から順に正しい場所へ「滲んで」
  戻っていく。アクセスされない key は [[p-fs.md]] §3.4 の anti-entropy
  （定期的な背景修復）が拾う。**miss 駆動が前景、anti-entropy が背景**、の二層。
- 修復もまた各ノードの局所判断であり、中央の rebalancer は存在しない。

### 3.4 窓は有界である — SWIM 収束との関係

ずれの窓の長さを支配するのは SWIM の収束時間 T_swim（≒ gossip 伝播ラウンド数 ×
`SWIM_PROBE_INTERVAL_MS`、region 内なら数ラウンド）である：

- **t < T_swim（収束前）**：計算は外れうる。read-k と WANT が肩代わりする。
  この間の保証は「**gossip フォールバックが到達可能な範囲に生きた複製が 1 つでも
  あれば、解決できる**」まで弱まる。だがゼロにはならない——これが「窓は開くが
  有界」の意味。
- **t > T_swim（収束後）**：全員のビューが揃い、計算が再び 1 ホップで当たる。
  repair-on-miss と anti-entropy が複製を正位置へ戻し終えれば、定常状態に復帰。

つまり本設計の一貫性の主張は正確にはこうだ：
**「ルックアップの正しさは membership の収束に追随する（eventually findable）。
収束の遅れは成功率の低下ではなく、ホップ数とレイテンシの増加として現れる。」**
読めなくなるのではなく、遅くなる。これは [[p-fs.md]] §3.5 の eventual consistency
の意味論と同じ姿勢である。

## 4. region 局所性 — 密に解決し、疎に上申する

[[regions.md]] の核——**region 内は密に、region 間は疎に**——をルックアップに
適用する。鍵は「どの空間で HRW を回すか」である。

### 4.1 二層の責任空間

- **region 層（密）**：region 内のメンバ集合だけを母集団に HRW を計算する
  `responsible_region(k, r)`。region 内で生まれたデータ・region 内で使う expert は、
  まずここに置かれ、ここで引かれる。RTT≤τ の世界なので、WANT ブロードキャストも
  read-k 並行打ちも安い。
- **global 層（疎）**：region を跨いで引く必要があるもの（他 region 産の block、
  遠くの expert、world オブジェクト）は、global WANT（coordinator ゲートウェイ
  経由・要約のみ・TTL 付き）で解決する。global 層では「全ノード母集団の HRW」を
  当てにしない——**global membership こそ最もずれている**からであり、跨ぎ通信は
  そもそも疎であるべきだからだ。

### 4.2 resolve の昇格順序

```
  resolve(k):
    [L] world-table キャッシュ                     … 0 ホップ
    [R1] responsible_region(k, r) へ read-k        … 1 ホップ・密
    [R2] region 内 WANT                            … ブロードキャスト・密
    [G1] global WANT (coordinator 経由・TTL 付き)  … 疎・要約
    [G2] 解決不能 → 呼び出し側へ「未発見」を返す（嘘の成功は返さない）
```

ほとんどのワークロードは locality を持つ——[[survival-network.md]] §4 の
「平常時は近傍ノードだけが薄く発火する」スパース性は、データ参照にもそのまま
成り立つと期待できる。**平常時は R1 で完結し、global 層はほぼ無音。有事
（region 全滅・大規模 churn・遠隔の知識が要る問い）にだけ G1 が発火する。**
ルックアップのトラフィック形状そのものが、survival-network の発火モデルと相似に
なる。これは偶然ではなく、同じ密/疎構造に乗せた必然である。

### 4.3 region 間複製との関係

region 内 r 複製だけでは region 全体の喪失（停電・分断）で key が消える。
[[p-fs.md]] §2.4 の erasure coding / region 跨ぎシャード配置がこれに答えるが、
ルックアップ基盤の責務はそこまで踏み込まない——**「region 跨ぎに置かれたものを
G1 で見つけられる」ことだけを保証し、何をどれだけ跨いで置くかは p-fs の複製政策に
委ねる**（責務の境界、§7.4 も参照）。

## 5. 既存資産マッピング — ほとんどの部品は、もう在る

| 部品 | 既存資産 | 本設計での役割 | 新規 / 既存 |
|---|---|---|---|
| membership・生死・RTT | `swim.c`（SWIM + RTT EWMA） | HRW の母集団 `dnode_table[]`、ずれ窓 T_swim の源 | **既存**（変更なし） |
| 近さの束ね・密/疎境界 | `region.c` / `region.h`（egocentric region, coordinator） | responsible_region の母集団、WANT のスコープ境界 | **既存**（変更なし） |
| スコープ付き配信 | `kdds.c` + [[regions.md]] §3.4 スコープ階層 | WANT/HAVE の搬送路（region / global トピック） | **既存**（R0 で導入済みの上に乗る） |
| 解決キャッシュ | `world.c` world-table（self-beacon・局所観測） | resolve 結果の記憶、鮮度管理 | **既存**（エントリ種別の追加のみ） |
| 局所勾配ゲーティング | `moe.c` `select_expert()`（utility = acc − a·RTT − b·pressure） | §7 expert 解決の**選好**側。lookup は「候補がどこか」、gating は「どれを選ぶか」 | **既存**（lookup と直交、§7.5） |
| 責任集合の計算 | — | `responsible(k, r)` HRW（状態なし・O(N)） | **新規**（小さい：ハッシュとソートのみ） |
| WANT / HAVE プロトコル | — | フォールバック解決＋repair-on-miss の引き金 | **新規**（K-DDS トピック 2 本＋ハンドラ） |
| repair-on-miss | `replica.c` / [[p-fs.md]] §3.4 anti-entropy | miss 駆動の前景修復として接続 | **接続**（押し込み先計算に HRW を流用） |

読み方：**新規に書くのは「責任計算」と「WANT/HAVE」の二つだけ**で、どちらも
状態をほとんど持たない。membership・region・搬送・キャッシュという状態を持つ
重い部品は、すべて既に在るものをそのまま使う。これは設計の手柄ではなく、
[[README.md]] の 5 レイヤーが最初から「Collective の部品は再利用される」前提で
積まれてきた結果である。

利用者側（この基盤の上に乗る三つの顔）：

- **p-fs**：`k = block hash`。resolve → block fetch。repair-on-miss が §3.4 の
  自己修復に直結。
- **分散ゲーティング（survival §7）**：`k = expert/capability の広告 id`。
  resolve は「候補の所在」を返し、`select_expert()` の局所勾配 utility が
  「どれに頼むか」を決める。**lookup は発見、gating は選好**——層が違う。
- **world オブジェクト**：`k = object id`（ノード・資源・知識単位）。world-table
  自体がキャッシュなので、最も自然に乗る。

## 6. 段階実装 L0→L3

[[p-fs.md]] P0→P4・[[regions.md]] R0→R3 と同じ流儀：各段が単独で動き、単独で
検証でき、次の段の前提になる。

### L0 — `responsible(k, r)`：状態なしの責任計算（最小・単体テスト可能）✅ 実装済

- `arch/common/lookup.c` + `include/lookup.h`。HRW の weight 計算と top-r 選出のみ。
- 入力は `dnode_table[]`（ALIVE のみ）。出力はノード ID の配列。
- スコアは sha256(key‖node_id) の先頭 8 バイトを 2×U4 で辞書順比較 → **aarch64/x86_64/i686 で byte-stable**
  （固定幅のみ・endianness 非依存）。同点は小さい node id へ。
- 検証：同一 membership を与えた 2 ノードが同一集合を返す／1 台抜いたとき動く key が最小限（L0 自己テスト）。

### L1 — read-k resolve + world-table キャッシュ ✅ 実装済

- `lookup_resolve(k)`：キャッシュ → responsible top-k へ順に問い合わせ。
- 解決エントリ（TTL 付き）を局所キャッシュ。誤エントリは L2 で1ホップ余計に掛かるだけで正しさは保つ。
- 検証：L1 自己テスト（L0 ランキングの上に乗るキャッシュ意味論）。

### L2 — WANT/HAVE フォールバック + repair-on-miss（未実装）

- K-DDS region スコープに `lookup/want`・`lookup/have` トピック。
- miss 時の region 内 WANT、解決時の push repair。
- 検証：**churn 注入テスト**——書き込み直後にノードを join/leave させ、ずれ窓の
  最中でも resolve が成功すること（成功率ではなくホップ数が劣化することを確認）。
  これが §1.2 のシナリオの直接の再現実験になる。

### L3 — global 昇格（coordinator ゲートウェイ・TTL・レート制限）

- global WANT の coordinator 経由転送、TTL、要求のレート制限・重複抑制。
- coordinator 不応答時の次点代行（§2.2 の縮退経路）。
- 検証：2 region 構成で、他 region 産 key の resolve／region 丸ごと切断からの復帰。
- ここまでで p-fs P1（block の分散 put/get）の足場が完成する。

各段とも、`net_relay.c` の教訓（per-packet スクラッチを task スタックに置かない
— `feedback_hosted_relay_stack_overflow`）を最初から守ること。WANT ハンドラは
ブロードキャスト受信なので、ホットパスである。

## 7. 正直な論点 — 解けていないこと、知っていて先送りすること

### 7.1 churn 窓の定量が無い

§3.4 で「窓は T_swim で有界」と書いたが、**T_swim の実測値も、窓中の read-k
成功率・WANT 到達率の実測値も、まだ無い**。global 層のずれは region 内より
はるかに大きく、収束も遅い。L2 の churn 注入テストが最初の実データになる。
それまで本ドキュメントの §3 は「論理的にはこうなるはず」以上の主張をしていない。
[[p-fs.md]] §6.1 の「churn 率に対するルックアップ成功率は実測しないと分からない」
という白状を、ここでも繰り返しておく。

### 7.2 hot key — 責任ノードは選べない

HRW は key を一様に散らすが、**アクセスは一様ではない**。全ノードが参照する
ホットな block / 人気 expert の責任 r 台は、自分では選んでいない負荷を浴びる。
緩和の手札は (a) world-table キャッシュ（ホットなものほどキャッシュが効く——
自然な負け方）、(b) HAVE 応答に「自分もキャッシュした」を含めて複製を滲ませる、
(c) 責任ノードが逼迫したら world ビーコンの pressure に現れ、moe 的 utility が
他の複製へ流す——だが (c) は lookup と gating の責務を跨ぐ（§7.5）。
**どこまでが lookup 基盤の仕事かは未決。** L1 のキャッシュだけで足りる規模の間は
先送りする。

### 7.3 Sybil — 名前空間がタダなら責任は奪える

HRW の責任は node_id のハッシュで決まる。**node_id を大量に名乗れる攻撃者は、
狙った key の top-r を自分の偽ノードで埋められる**（eclipse）。そうなれば
「持っていない」と答え続けるだけで key を消せる——複製も read-k も、母集団が
汚染されていれば無力である。relay v2 の HMAC はリンクの真正性しか守らず、
**「この node_id を名乗ってよいか」は誰も検証していない**。[[p-fs.md]] §6.4・
[[regions.md]] §6.4 の信頼問題と同根で、解は ID 取得へのコスト付与（鍵ベース ID、
参加の社会的コスト）だが、鍵管理レイヤーはまだ存在しない。**現状の正直な答え：
本基盤は協力的なノード集合を前提とし、敵対的環境は守備範囲外。** これを文書で
明示すること自体が、いま打てる唯一の手である。

### 7.4 p-fs 複製政策・erasure coding との合成 — 責務の境界が薄い

本基盤は「top-r に置けば top-r で引ける」と言うが、[[p-fs.md]] §2.4 の erasure
coding はシャードを**わざと**広く（region 跨ぎに）撒く。シャード配置が HRW の
責任集合と一致しないなら、lookup はシャードごとの key（shard id）で引くのか、
block id から責任ノードがシャード地図を持つのか——**後者は「地図」という小さな
索引の再導入であり、危うい**。シャード id ごとの HRW（地図なし）に倒すのが
不変条件には忠実だが、再構成時に k 回の resolve が要る。p-fs P3（erasure coding）
の設計時に決める。先に決め打ちしない。

### 7.5 lookup と gating の二層は本当に分離できるか

§5 で「lookup は発見、gating は選好」と切ったが、§7.2(c) が示す通り境界は漏れる。
発見の段階で「近い・空いている候補を優先して返す」最適化を入れたくなった瞬間、
lookup が utility を知る必要が生じ、二層は癒着する。癒着は単純さを殺すが、
分離は無駄なホップを生む。**当面は厳格分離（lookup は所在のみ・順序は HRW 順位
のみ）で始め、実測でホップ数が痛くなってから初めて再訪する**——抽象の純潔より
実測を信じるのは、この計画全体の流儀である。
